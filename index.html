下午帮一位朋友处理了一张理论模型的概念框图。

他发来一张经典的框图截图，希望做成类似风格，但又不想用 Visio 或 PPT 画，问能不能用 Nano Banana。我直接判断不太合适。Nano Banana 生成视觉效果可以，但做结构严谨的关系图时，经常会把逻辑关系搞复杂，线条也容易变形，不太稳。

我建议他试试用 Gemini 直接生成 SVG。坦白说，我一开始也不确定效果怎么样。结果今天自己试了一下，把原图直接贴进去生成，出来的效果相当惊艳。确实有一些细节问题，比如线框尺寸和字体比例不够协调，但整体布局非常可观，结构基本是对的。

我把生成的 SVG 发给他，他明显有点震惊。因为一旦有了可编辑的 SVG，后面只需要做微调，而不是从零开始画。

微调时我用了 Inkscape，但这个软件对我来说完全陌生，界面逻辑也不算直观，目前操作还比较生疏。很多细节我暂时处理不了，只能删减一些明显多余的线条和文字。技术上还有盲区，不过路径已经清晰，效率比传统方式高太多，剩下的就是熟练度问题。

后来他自己用 Gemini 试了一下，但用的不是 Pro 版本，生成速度很慢。我又帮他跑了一次。他给我一段文字描述，我让 AI 根据描述生成框图草稿，先用 Banana 生成一个渲染版，再把框图转成 SVG，效果相当稳定。这种组合式工作流反而很顺。

最后我用 Inkscape 简单清理了一些多余元素，就把成品发给他。进一步的精细调整我现在还做不了，只能慢慢练。

整体来看，这件事验证了一点：在结构化图形这类任务上，AI 生成 SVG 的路径已经非常可用。真正的瓶颈不在生成，而在人工微调能力。熟练度一上来，这种工作会变得异常高效。

昨天晚上开始折腾 Zotero 的仓库。它本身是非常成熟、也非常著名的文献管理软件，插件体系很丰富。但这些插件大多停留在旧时代的思路里。这几年 AI 发展太快了，Zotero 的生态在这方面明显有些滞后，我觉得有必要往更底层挖一挖。

运气不错，我发现它的数据库文件是可以直接访问和解析的，并没有加密。这一下就打开了局面。我可以直接从数据库里提取文献目录、元数据等信息，绕开原本的界面层。基于这个数据库，我做了一个简单的前端，有点像一个轻量版的 Zotero 界面。界面本身并不复杂，但有了它，我就可以直接调用自己定制的功能，比如用 AI 去读取和分析文献文件。整个流程突然变得顺滑了很多。

这个项目我感觉是有延展性的，后面完全可以继续往下走。整体实现基本都是用 Python。额外做了两个核心功能模块：

一个是通过现成的库，把 PDF 文档转成结构化的数据格式，方便 AI 直接读取和分析；

另一个是通过 Claude Agent SDK，对每篇文章做自动分析。单篇分析确实需要时间，但整体效果是值得的，尤其在规模化处理时优势会逐渐显现。

严格说来，除了"数据库可以直接被解析"这个发现之外，其余几个环节我之前都做过。真正让我兴奋的是这次意识到：很多软件在 AI 时代，其实可以绕开表层接口，直接下沉到数据层去重构工作流。这种思路的变化，对我来说是一次观念上的转折。

整体感觉是，进入 AI 时代之后，软件进一步扁平化几乎成了一种趋势。界面不再是中心，数据与模型的连接才是中心。谁能把这条路打通，谁就真正获得了效率的杠杆。

终于把博客自动同步到 Telegram 频道的功能彻底搞定了。

回顾一下这次折腾的过程，其实核心逻辑不难，细节全是坑：

1. 基础链路：Bot + Actions

  • 申请机器人：找 BotFather 申请机器人，拉进频道当管理员，拿 Token 和 Chat ID。这步最简单。
  • 自动化脚本：写了个 Node.js 脚本，配合 GitHub Actions。每次代码 push 到 main 分支时，用 git diff 算出新增的 Markdown 文件，解析出标题和链接发给 Bot。

2. 问题一：文件重命名检测失效

  • 现象：修改了文件名（如 v1.md -> v2.md）后，推送没有触发通知。
  • 原因：Git 将此操作识别为 重命名 (Rename)，而脚本最初只检测 新增 (Add)。
  • 解决：将 git diff 的过滤器从 A 升级为 ACR，同时覆盖 Add、Copy、Rename 三种情况。

3. 问题二：Instant View 规则报错

  • 现象：IV 模板测试时，提示 <img> is not supported in <p>。
  • 原因：Markdown 渲染器默认将图片包裹在 <p> 标签里，但 IV 规范不允许。
  • 解决：在 IV 规则中加入 @split_parent: //p/img，强制将图片与父级段落拆开。

4. 问题三：Web 端链接无法打开

  • 现象：App 端点击 t.me/iv?... 链接能秒开，但 Web 端点击后无反应或报错。
  • 原因：Telegram Web 对 IV 链接的支持极差。
  • 尝试1（隐形链接）：在消息开头插入零宽空格 [\u200B](IV链接)，正文保留原始链接。这能在 App 端触发卡片，但依然不够优雅。
  • 尝试2（官方方案）：升级到 Telegram Bot API 的 link_preview_options。在 API 调用中显式指定 url: "t.me/iv?..." 用于生成预览卡片，而正文链接保持原始网址。这是目前最稳健的方案。

5. 问题四：通知没有预览卡片（时序问题）

  • 现象：消息能发送，但无论 App 还是 Web 都没有预览卡片。
  • 原因：通知步骤在部署步骤之前执行。当 Telegram 服务器收到链接去抓取时，新文章还未上线，返回 404，导致预览生成失败。
  • 解决：调整 GitHub Actions 工作流顺序，将通知步骤移到部署之后，并增加 10 秒延迟等待 CDN 生效。

最终流程

写文章 -> Push -> 自动触发 Action -> 先部署 -> 等待 10s -> 再通知 -> 频道秒推 (带 Instant View)。

阅读，应该读两次

读书这件事，很多人都有类似的挫败感：书买回来了，翻完了，划了线，做了笔记。合上书那一刻，心里却有点空。过几周再提起，只剩下一点模糊的印象，像是去过一个地方，却说不清它长什么样。

更糟的是，有些书在第一次读的时候显得“很有道理”，过一阵回头看，却发现当初被打动的段落，站不住脚，甚至有点可疑。可时间已经花了，笔记已经做了，人也懒得再翻第二遍。

于是，书读得越来越多，真正留下来的越来越少。书架变高，脑子并没有同步扩容。

这个问题存在了很久，只是我们一直默认它是“读书的正常代价”。但换个角度看，也许问题不在书，也不在你，而在读法。

【1】我的解法：两次阅读，两种任务

这个方法听起来简单得有点寒酸：同一本书，读两次。 很多人会下意识反对。时间已经这么紧，哪还有空把一本书读两遍？书还那么多，世界还那么大。

但关键在于，这两次阅读承担的任务完全不同。

第一次，是探索；第二次，是建造。

如果你把阅读当成一次性工程，试图在第一遍就完成理解、判断、吸收、内化，失败几乎是必然的。人的认知系统不擅长在未知环境中一次性做完所有事。

【2】第一次读：扫一遍路，让大脑摸地形

第一次读书，目标要刻意放低。

这一步不追求“读懂”，只追求“读过”。不要求记住细节，不要求形成观点，甚至不要求完全同意作者。

只做三件事：知道这本书在讲什么，大概怎么讲，哪些地方让你停顿了一下。

这时候做笔记要克制。标记可以有，但别急着写长评、下判断。很多第一次读就写得很满的笔记，回头看往往像情绪记录，价值不高。

这一遍更像是在陌生城市里走一圈。你知道了主干道在哪，哪些地方热闹，哪些地方绕。至于哪家店好吃，哪条路适合长期生活，现在下结论太早。

很多书，尤其是思想性强的书，本来就不可能在第一次阅读时被真正理解。你缺的是语境、问题意识和判断坐标，而这些东西，只能在走过一遍之后才慢慢浮现。

【3】第二次读：回到关键处，开始搭结构

第二次阅读，才是真正的“读书”。

这时你已经知道作者的大致路线，也知道哪些地方重要，哪些地方只是铺垫。你不再被文字牵着走，而是带着问题回去。

这一次，笔记才有价值。你可以拆作者的论证结构，看他用的例子是否成立，前后是否自洽。你可以明确地同意、不同意，甚至修正他的结论。

很多真正有收获的时刻，恰恰发生在第二遍。第一次觉得“好有道理”的段落，可能会在第二次暴露出偷换概念；第一次觉得晦涩的章节，反而因为整体轮廓清楚了，突然变得顺畅。

这就像看建筑图纸。第一次只是看外形，第二次才开始理解承重结构和力的走向。真正能学走样东西的，是后者。

【4】为什么两次反而更省时间

乍一看，读两遍显然更慢。

但单次阅读的隐性成本很高。你在第一遍里反复卡壳，反复回读，为了搞懂一个局部，不断打断整体理解。读完之后，还要花时间回忆、补救、查资料。

两次阅读把成本分摊了。第一遍容许模糊，第二遍精准用力。总时间未必翻倍，但理解深度往往成倍提升。

更重要的是，第二遍会显著降低“读了却没用”的概率。你开始知道哪些书值得反复读，哪些书读一遍就够。这种筛选能力，本身就是阅读经验的一部分。

说到底，阅读不是摄入信息，而是重组认知。第一次只是把材料搬进来，第二次才谈得上加工。

世界上真正改变过人的书，几乎没有是只读一遍的。两次阅读，并不奢侈，它只是对理解这件事多给了一点耐心。

（受宝玉老师 @dotey 的文章《AI 时代的代码审核：写两遍，反而更快》启发。很多事情都应当做两遍，这背后应该有一套通用的方法论 ）

为谁创作？——平台、读者or你自己？

很多经验贴都喜欢给萌新创作者灌输一条所谓的金科玉律：“要为用户创造价值。”这句话听起来无可辩驳。然而，当我们深入剖析内容平台的运作机制，就会发现这句箴言不仅不准确——它更是一个陷阱。

  1. 价值的真相：你在为平台打工，而非用户

“为用户创造价值”的说法之所以具有欺骗性，是因为它掩盖了平台的真实目标。平台并非慈善机构，其核心商业模式是制造和聚集海量流量，从而获取广告收益。因此，平台真正需要的，是能够最大限度吸引用户注意力、让用户沉迷其中的内容，而不是内容本身质量有多高。

在这种模式下，创作者所谓的“创造价值”，其本质是在帮助平台创造流量价值。在这笔交易中，你创造的价值首先服务于平台的商业底线。至于它是否服务于你的读者——或者你自己——充其量只是一个次要的考虑。

所谓的“创造价值”是在为平台创造价值，为他们的流量创造价值，然后你从中获得一些少量抽成。

  1. 流量的悖论：失去自我的创作者终将被抛弃

平台的算法制造了一个残酷的现实：一个只擅长搞流量的创作者，即便产出的是垃圾，也能风生水起；而一个能创作出高质量内容却不懂流量技巧的创作者，则注定被埋没。这不是系统的漏洞，这恰恰就是系统本身。

这就引出了一个核心悖论：如果一位创作者过度地为了流量而生产，就很容易在这个过程中“失去自我”。当创作的唯一目标变成追逐平台的算法和用户的瞬时兴趣时，创作者独特的思考和风格便荡然无存。而一个没有了“自我”的创作者，在平台眼中就只是一个消耗品。等到他那些获取流量的技能不再有效时，平台会毫不犹豫地将他彻底抛弃。

不知刷推是否容易把人变得脑残，反正我是如此！

当然也不光X，其它的平台也好不哪去。我的个人体会就是，但凡能成瘾的事情都需要克制，尤其是互联网平台的内容创作者，不然脑残几乎不可避免，理由大致有如下几点：

  1. 刷推具有成瘾性。就像抽烟一样，抽得越多烟瘾越大，短暂的离开会让自己变得暴躁。一开始潜水时，觉得没意思之后，随时可以把app卸掉。后来开始发推之后，就很难如此轻松写意了。我感触最深的是涨粉比较多的那两天，骑个车子，每几分钟都想看一下自己是不是涨粉了。

  2. 成瘾性影响了休息，尤其是X是个国际平台，不会因为到了夜里就变得消停。经常不知不觉就两三点钟了，然后一大早像个傻子一样起床，脑子里一团糨糊。

  3. 刷推的即时性满足让我少了许多深度阅读。且不说读书，就算是以前经常阅读的Hacker News上的文章都不怎么刷了。有不少人会搬运其收录的文章，但是在推上面对这些文章，我所做基本上就是扔进收藏夹吃灰。

  4. 不再愿意去写稍微长一点的东西，因为字数限制，对平台来说，写得东西或长或短其实都是一回事。与其把内容表达完整，还不如把第一句写好意义大。一切的努力都是为了获得那一两秒对读者的吸引。

  5. 帖子的选题开始变得迁就。明显感觉有一些话题更容易获得热度，但几乎共同的一点：这些话题都是烂大街的话题。其实有很多真正值得思考但对大众而言过于细枝末节，无人关注，自然也就不会成为写作的选题。

如果每天投入大量时间、舍弃掉自己的个性以讨好平台能够获得足够的流量和金钱回报，当然也可以接受。搞钱嘛，不寒碜。

但以我当前的处境，还是不得不好好思考一下。我确实感觉自己每天像个傻叉一样（或者说，一开始就是）...

流量焦虑症

现在写推文有种强烈的被压榨感。

在社媒灌水的生涯中，感觉自己被压榨是常态，如有文章爆火或者粉丝猛涨，这种糟糕的感觉会缓和一些。

这种被压榨感可以统称为“流量焦虑症”。

我相信有流量的大v也有焦虑症，比如流量能够带来收益，他们可能会认为过多的收益配平台拿走了；看到英推的低保发得比简中区更多会认为被老马歧视了。当然，搞一个不到千粉的小号，这些体验我都没有过。

我介意的是，自己写了很多内容，其实也没那么差，但是流量全被那些大号分走了，而他们的内容其实很多也都是低质量的哗众取宠贴。

我也偶尔会因为写点哗众取宠的内容意外小火一把，这种时候“流量焦虑症”可以暂时缓解，但在稍感兴奋之余又会感慨：这破玩意都能火？此时难免会为自己写的其他内容感到不值。

所以，“流量焦虑症”可能是一种绝症，各种视角下产生的不被公平对待的感觉都会让人不愉快。

不光是写推文如此，之前写公众号和知乎等帖子也类似。

可能只有彻底脱离这个圈子方能解除，但是为什么不去脱离呢？
