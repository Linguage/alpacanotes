15:T2b3b,<p>Telegram 的 Instant View（IV）可以让用户在 Telegram 客户端里直接阅读网页正文，不用跳转浏览器。对内容站来说，文章链接带上 <code>INSTANT VIEW</code> 按钮，阅读体验会好不少。</p>
<p>但要让 IV 稳定工作，特别是对部署在 GitHub Pages 上的静态站点来说，需要把页面标记、IV 规则、Bot 消息和部署时序几个环节串起来。这篇文章按操作顺序整理了关键步骤。</p>
<h2 id="1-页面端加语义标记">1. 页面端：加语义标记</h2>
<p>IV 模板需要从页面 HTML 中提取标题、正文、作者、发布时间等信息。最直觉的做法是靠 CSS 类名来定位——但这非常脆弱。你用 Tailwind 生成的 <code>text-xl</code>、<code>mt-16</code> 之类的类名随时可能因为样式调整而变化，IV 规则会悄悄失效，而且没有任何报错。</p>
<p>更稳妥的做法是在页面模板中加一组专用的 <code>data-iv-*</code> 属性：</p>
<pre><code>&#x3C;article data-iv-page="post">
  &#x3C;header data-iv-header="true">
    &#x3C;h1 data-iv-title="true">{post.title}&#x3C;/h1>
    {post.subtitle &#x26;&#x26; (
      &#x3C;p data-iv-subtitle="true">{post.subtitle}&#x3C;/p>
    )}
    &#x3C;div>
      &#x3C;time dateTime={post.date} data-iv-published={String(publishedUnix)}>
        {publishedLabel}
      &#x3C;/time>
      &#x3C;span data-iv-author="true">{post.author}&#x3C;/span>
    &#x3C;/div>
  &#x3C;/header>

  &#x3C;div data-iv-body="true"
       dangerouslySetInnerHTML={{ __html: post.contentHtml }}
  />

  {/* 不希望 IV 抓取的区域 */}
  &#x3C;nav data-iv-ignore="true">...&#x3C;/nav>
&#x3C;/article>
</code></pre>
<p>几个要点：</p>
<ul>
<li><code>data-iv-title</code>、<code>data-iv-body</code>、<code>data-iv-author</code> 分别标记标题、正文和作者</li>
<li><code>data-iv-published</code> 放在 <code>&#x3C;time></code> 元素上，值为 Unix 时间戳（IV 引擎可以直接解析）</li>
<li><code>data-iv-ignore</code> 标记导航栏、侧边栏、评论区等不应出现在阅读视图中的元素</li>
</ul>
<p>同时检查一下页面的 <code>&#x3C;link rel="canonical"></code> 是否包含了正确的部署子路径。如果你的站点部署在 <code>/alpacanotes</code> 下，canonical URL 也要带上这个前缀。这个问题浏览器不在乎，但 Telegram 在抓取和缓存时会参考 canonical。</p>
<h2 id="2-iv-规则编写与同域名兼容">2. IV 规则：编写与同域名兼容</h2>
<p>到 <a href="https://instantview.telegram.org/my/">Telegram Instant View Editor</a> 编写规则。规则用 XPath 语法告诉 IV 引擎从页面中提取哪些内容。</p>
<p>如果你的域名下只有一套页面结构，规则很简单：</p>
<pre><code class="language-yaml">~version: "2.1"

body:           //*[@data-iv-body]
title:          //*[@data-iv-title]
subtitle:       //*[@data-iv-subtitle]
author:         //*[@data-iv-author]
published_date: //*[@data-iv-published]/@data-iv-published

@split_parent:  //p/img
@remove:        //*[@data-iv-ignore]
</code></pre>
<h3 id="同域名多模板的情况">同域名多模板的情况</h3>
<p>如果同一个域名下还跑着其他站点（比如主站的文档页），HTML 结构可能完全不同。IV 规则是按域名绑定的，一个域名只有一份规则。这时需要用 XPath 的 <code>|</code>（或）运算符做双路匹配：</p>
<pre><code class="language-yaml">~version: "2.1"

body: //*[@data-iv-body] | //article[contains(@class, "docs-content")]//div[contains(@class, "md-theme-amp")]
title: //*[@data-iv-title] | //article[contains(@class, "docs-content")]//div[contains(@class, "md-theme-amp")]//h1[1]
subtitle: //*[@data-iv-subtitle] | //article[contains(@class, "docs-content")]//div[contains(@class, "md-theme-amp")]//h1[1]/following-sibling::p[1]
author: //*[@data-iv-author] | //article[contains(@class, "docs-content")]//div[contains(@class, "text-muted") and contains(@class, "text-sm")][1]/span[1]
published_date: //*[@data-iv-published]/@data-iv-published | //article[contains(@class, "docs-content")]//div[contains(@class, "text-muted") and contains(@class, "text-sm")][1]/span[last()]

@split_parent: //p/img
@remove: //*[@data-iv-ignore] | //article[contains(@class, "docs-content")]//div[contains(@class, "mb-4")]

@set_attr(width, "auto"): //img
</code></pre>
<p>规则会从左到右尝试匹配，第一个命中的生效。把 <code>data-iv-*</code> 放在前面，回退规则放在 <code>|</code> 后面。</p>
<p>写好之后在编辑器里用几个不同页面测试，确认都能正确提取，然后点 <strong>Mark as Published</strong>，会得到一个 <code>rhash</code>。把它存到 GitHub Secrets 的 <code>TELEGRAM_IV_RHASH</code> 里。</p>
<h2 id="3-bot-消息构造">3. Bot 消息构造</h2>
<p>有了 <code>rhash</code>，就可以构造 IV 链接了：</p>
<pre><code>https://t.me/iv?url=&#x3C;encoded_article_url>&#x26;rhash=&#x3C;your_rhash>
</code></pre>
<p>通过 Bot API 发消息时，可以用 <code>link_preview_options</code> 参数指定预览 URL：</p>
<pre><code class="language-javascript">const ivUrl = `https://t.me/iv?url=${encodeURIComponent(articleUrl)}&#x26;rhash=${rhash}`;

const body = {
  chat_id: channelId,
  text: messageText,
  parse_mode: 'HTML',
  link_preview_options: {
    url: ivUrl,
    prefer_large_media: true,
    show_above_text: true
  }
};

await fetch(`https://api.telegram.org/bot${token}/sendMessage`, {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify(body)
});
</code></pre>
<h3 id="注意事项">注意事项</h3>
<p><code>link_preview_options</code> 的行为和用户手动粘贴链接不完全一样。几个实际经验：</p>
<ul>
<li>消息文本中最好也包含原始文章链接（作为阅读兜底），不要只依赖 IV 链接</li>
<li>同一条消息里不要塞太多链接，否则 Telegram 可能会选错一条来生成预览</li>
<li>新发布的链接效果最好；旧链接可能因为 Telegram 缓存而无法及时更新 IV 状态</li>
</ul>
<h2 id="4-github-pages-部署两个容易踩的坑">4. GitHub Pages 部署：两个容易踩的坑</h2>
<h3 id="41-nojekyll-文件">4.1 <code>.nojekyll</code> 文件</h3>
<p>如果你用 Next.js（或任何会生成 <code>_next</code> 目录的框架）部署到 GitHub Pages，<strong>必须</strong>在发布根目录放一个空的 <code>.nojekyll</code> 文件。</p>
<p>原因：GitHub Pages 默认启用 Jekyll 处理，而 Jekyll 会忽略所有下划线开头的目录。<code>_next</code> 里放着你全部的 CSS 和 JS 资源——被忽略之后，页面就变成光秃秃的纯文本，CSS/JS 全 404。</p>
<p>如果你用手写 shell 脚本部署，不要忘了这一步：</p>
<pre><code class="language-bash">cp -R ./out/. "${deploy_dir}/"
touch "${deploy_dir}/.nojekyll"   # 关键
</code></pre>
<p>这个问题的症状很容易被误判为前端代码错误，因为 HTML 本身是正常的，只是样式全丢了。</p>
<h3 id="42-发布时序先确保页面在线再发通知">4.2 发布时序：先确保页面在线，再发通知</h3>
<p><strong>这是整个流程中最重要的一条。</strong></p>
<p>代码推送到 <code>gh-pages</code> 分支之后，GitHub Pages 的 CDN 并不是立刻就能返回新内容。可能要几十秒，甚至一两分钟。如果 Bot 在部署步骤完成后立刻发通知，Telegram 去抓取页面时拿到的可能是旧版本、404 或者不完整的页面。IV 引擎匹配失败，卡片不会挂上 <code>INSTANT VIEW</code> 按钮。更糟的是 Telegram 会缓存这个失败的结果。</p>
<p>解决方案是在部署和通知之间加一个等待步骤，轮询目标 URL 直到确认新页面已经可以正常访问：</p>
<pre><code class="language-javascript">async function waitForTarget(target) {
  const MAX_ATTEMPTS = 18;  // 最多 18 次
  const DELAY_MS = 10000;   // 每次间隔 10 秒

  for (let attempt = 1; attempt &#x3C;= MAX_ATTEMPTS; attempt++) {
    // 加随机参数绕过 CDN 缓存
    const probeUrl = `${target.url}?deploy_check=${Date.now()}`;

    try {
      const response = await fetch(probeUrl, {
        headers: { 'cache-control': 'no-cache' }
      });
      const html = await response.text();

      // 检查 HTTP 200 且页面包含预期内容
      const ready = response.ok &#x26;&#x26; (
        html.includes('data-iv-body') ||
        html.includes(target.expectedTitle)
      );

      if (ready) return;
    } catch (error) {
      // 网络错误，继续重试
    }

    await new Promise(r => setTimeout(r, DELAY_MS));
  }

  throw new Error(`Timed out waiting for: ${target.url}`);
}
</code></pre>
<p>核心思路：</p>
<ul>
<li>查询参数 <code>deploy_check=${Date.now()}</code> 让每次请求的 URL 都不同，避免 CDN 返回缓存</li>
<li>检查标准不只是 HTTP 200，还要确认页面内容包含 <code>data-iv-body</code> 或文章标题——防止 CDN 返回旧版页面</li>
<li>最多等 3 分钟（18 次 × 10 秒），超时则报错中断部署流程</li>
</ul>
<p>在 GitHub Actions 的 deploy workflow 中，把这个等待步骤放在部署和通知之间：</p>
<pre><code class="language-yaml">- name: Deploy to GitHub Pages
  run: # ...部署脚本...

- name: Wait for deployment propagation
  run: node scripts/wait-for-publication.js

- name: Cool down before notify
  run: sleep 20

- name: Notify Telegram
  run: node scripts/telegram-notify.js
</code></pre>
<p><code>sleep 20</code> 是轮询通过之后的额外冷却时间。CDN 传播不是瞬时完成的，多等 20 秒可以让更多边缘节点同步完毕。</p>
<h2 id="5-telegram-客户端缓存">5. Telegram 客户端缓存</h2>
<p>即使以上全部配置正确，你可能仍然会遇到一个现象：同一条 IV 链接第一次打开正常，再次打开偶尔白屏。</p>
<p>这是 Telegram 客户端自身的缓存/渲染行为，不在站点侧能控制的范围内。判断方法很简单：如果第一次能打开，说明规则和页面都没问题；如果是重复打开才出问题，那就是客户端侧的事。</p>
<p>务实的做法是：消息里始终保留原始文章链接作为兜底，验证 IV 效果时用新链接而不是反复测试同一条旧消息。</p>
<h2 id="总结一下关键步骤">总结一下关键步骤</h2>
<ol>
<li>页面模板加 <code>data-iv-*</code> 语义标记</li>
<li>在 IV 编辑器中编写基于这些标记的规则，发布拿到 <code>rhash</code></li>
<li>Bot 消息用 <code>link_preview_options</code> 挂 IV 链接，同时保留原始链接</li>
<li>部署目录放 <code>.nojekyll</code></li>
<li><strong>部署后轮询确认页面在线，再发通知</strong>——这一条最容易漏，也最关键</li>
</ol>

<p>同时检查一下页面的 <code>&#x3C;link rel="canonical"></code> 是否包含了正确的部署子路径。如果你的站点部署在 <code>/alpacanotes</code> 下，canonical URL 也要带上这个前缀。这个问题浏览器不在乎，但 Telegram 在抓取和缓存时会参考 canonical。</p>
<h2 id="2-iv-规则编写与同域名兼容">2. IV 规则：编写与同域名兼容</h2>
<p>到 <a href="https://instantview.telegram.org/my/">Telegram Instant View Editor</a> 编写规则。规则用 XPath 语法告诉 IV 引擎从页面中提取哪些内容。</p>
<p>如果你的域名下只有一套页面结构，规则很简单：</p>
<pre><code class="language-yaml">~version: "2.1"

body:           //*[@data-iv-body]
title:          //*[@data-iv-title]
subtitle:       //*[@data-iv-subtitle]
author:         //*[@data-iv-author]
published_date: //*[@data-iv-published]/@data-iv-published

@split_parent:  //p/img
@remove:        //*[@data-iv-ignore]
</code></pre>
<h3 id="同域名多模板的情况">同域名多模板的情况</h3>
<p>如果同一个域名下还跑着其他站点（比如主站的文档页），HTML 结构可能完全不同。IV 规则是按域名绑定的，一个域名只有一份规则。这时需要用 XPath 的 <code>|</code>（或）运算符做双路匹配：</p>
<pre><code class="language-yaml">~version: "2.1"

body: //*[@data-iv-body] | //article[contains(@class, "docs-content")]//div[contains(@class, "md-theme-amp")]
title: //*[@data-iv-title] | //article[contains(@class, "docs-content")]//div[contains(@class, "md-theme-amp")]//h1[1]
subtitle: //*[@data-iv-subtitle] | //article[contains(@class, "docs-content")]//div[contains(@class, "md-theme-amp")]//h1[1]/following-sibling::p[1]
author: //*[@data-iv-author] | //article[contains(@class, "docs-content")]//div[contains(@class, "text-muted") and contains(@class, "text-sm")][1]/span[1]
published_date: //*[@data-iv-published]/@data-iv-published | //article[contains(@class, "docs-content")]//div[contains(@class, "text-muted") and contains(@class, "text-sm")][1]/span[last()]

@split_parent: //p/img
@remove: //*[@data-iv-ignore] | //article[contains(@class, "docs-content")]//div[contains(@class, "mb-4")]

@set_attr(width, "auto"): //img
</code></pre>
<p>规则会从左到右尝试匹配，第一个命中的生效。把 <code>data-iv-*</code> 放在前面，回退规则放在 <code>|</code> 后面。</p>
<p>写好之后在编辑器里用几个不同页面测试，确认都能正确提取，然后点 <strong>Mark as Published</strong>，会得到一个 <code>rhash</code>。把它存到 GitHub Secrets 的 <code>TELEGRAM_IV_RHASH</code> 里。</p>
<h2 id="3-bot-消息构造">3. Bot 消息构造</h2>
<p>有了 <code>rhash</code>，就可以构造 IV 链接了：</p>
<pre><code>https://t.me/iv?url=&#x3C;encoded_article_url>&#x26;rhash=&#x3C;your_rhash>
</code></pre>
<p>通过 Bot API 发消息时，可以用 <code>link_preview_options</code> 参数指定预览 URL：</p>
<pre><code class="language-javascript">const ivUrl = `https://t.me/iv?url=${encodeURIComponent(articleUrl)}&#x26;rhash=${rhash}`;

const body = {
  chat_id: channelId,
  text: messageText,
  parse_mode: 'HTML',
  link_preview_options: {
    url: ivUrl,
    prefer_large_media: true,
    show_above_text: true
  }
};

await fetch(`https://api.telegram.org/bot${token}/sendMessage`, {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify(body)
});
</code></pre>
<h3 id="注意事项">注意事项</h3>
<p><code>link_preview_options</code> 的行为和用户手动粘贴链接不完全一样。几个实际经验：</p>
<ul>
<li>消息文本中最好也包含原始文章链接（作为阅读兜底），不要只依赖 IV 链接</li>
<li>同一条消息里不要塞太多链接，否则 Telegram 可能会选错一条来生成预览</li>
<li>新发布的链接效果最好；旧链接可能因为 Telegram 缓存而无法及时更新 IV 状态</li>
</ul>
<h2 id="4-github-pages-部署两个容易踩的坑">4. GitHub Pages 部署：两个容易踩的坑</h2>
<h3 id="41-nojekyll-文件">4.1 <code>.nojekyll</code> 文件</h3>
<p>如果你用 Next.js（或任何会生成 <code>_next</code> 目录的框架）部署到 GitHub Pages，<strong>必须</strong>在发布根目录放一个空的 <code>.nojekyll</code> 文件。</p>
<p>原因：GitHub Pages 默认启用 Jekyll 处理，而 Jekyll 会忽略所有下划线开头的目录。<code>_next</code> 里放着你全部的 CSS 和 JS 资源——被忽略之后，页面就变成光秃秃的纯文本，CSS/JS 全 404。</p>
<p>如果你用手写 shell 脚本部署，不要忘了这一步：</p>
<pre><code class="language-bash">cp -R ./out/. "${deploy_dir}/"
touch "${deploy_dir}/.nojekyll"   # 关键
</code></pre>
<p>这个问题的症状很容易被误判为前端代码错误，因为 HTML 本身是正常的，只是样式全丢了。</p>
<h3 id="42-发布时序先确保页面在线再发通知">4.2 发布时序：先确保页面在线，再发通知</h3>
<p><strong>这是整个流程中最重要的一条。</strong></p>
<p>代码推送到 <code>gh-pages</code> 分支之后，GitHub Pages 的 CDN 并不是立刻就能返回新内容。可能要几十秒，甚至一两分钟。如果 Bot 在部署步骤完成后立刻发通知，Telegram 去抓取页面时拿到的可能是旧版本、404 或者不完整的页面。IV 引擎匹配失败，卡片不会挂上 <code>INSTANT VIEW</code> 按钮。更糟的是 Telegram 会缓存这个失败的结果。</p>
<p>解决方案是在部署和通知之间加一个等待步骤，轮询目标 URL 直到确认新页面已经可以正常访问：</p>
<pre><code class="language-javascript">async function waitForTarget(target) {
  const MAX_ATTEMPTS = 18;  // 最多 18 次
  const DELAY_MS = 10000;   // 每次间隔 10 秒

  for (let attempt = 1; attempt &#x3C;= MAX_ATTEMPTS; attempt++) {
    // 加随机参数绕过 CDN 缓存
    const probeUrl = `${target.url}?deploy_check=${Date.now()}`;

    try {
      const response = await fetch(probeUrl, {
        headers: { 'cache-control': 'no-cache' }
      });
      const html = await response.text();

      // 检查 HTTP 200 且页面包含预期内容
      const ready = response.ok &#x26;&#x26; (
        html.includes('data-iv-body') ||
        html.includes(target.expectedTitle)
      );

      if (ready) return;
    } catch (error) {
      // 网络错误，继续重试
    }

    await new Promise(r => setTimeout(r, DELAY_MS));
  }

  throw new Error(`Timed out waiting for: ${target.url}`);
}
</code></pre>
<p>核心思路：</p>
<ul>
<li>查询参数 <code>deploy_check=${Date.now()}</code> 让每次请求的 URL 都不同，避免 CDN 返回缓存</li>
<li>检查标准不只是 HTTP 200，还要确认页面内容包含 <code>data-iv-body</code> 或文章标题——防止 CDN 返回旧版页面</li>
<li>最多等 3 分钟（18 次 × 10 秒），超时则报错中断部署流程</li>
</ul>
<p>在 GitHub Actions 的 deploy workflow 中，把这个等待步骤放在部署和通知之间：</p>
<pre><code class="language-yaml">- name: Deploy to GitHub Pages
  run: # ...部署脚本...

- name: Wait for deployment propagation
  run: node scripts/wait-for-publication.js

- name: Cool down before notify
  run: sleep 20

- name: Notify Telegram
  run: node scripts/telegram-notify.js
</code></pre>
<p><code>sleep 20</code> 是轮询通过之后的额外冷却时间。CDN 传播不是瞬时完成的，多等 20 秒可以让更多边缘节点同步完毕。</p>
<h2 id="5-telegram-客户端缓存">5. Telegram 客户端缓存</h2>
<p>即使以上全部配置正确，你可能仍然会遇到一个现象：同一条 IV 链接第一次打开正常，再次打开偶尔白屏。</p>
<p>这是 Telegram 客户端自身的缓存/渲染行为，不在站点侧能控制的范围内。判断方法很简单：如果第一次能打开，说明规则和页面都没问题；如果是重复打开才出问题，那就是客户端侧的事。</p>
<p>务实的做法是：消息里始终保留原始文章链接作为兜底，验证 IV 效果时用新链接而不是反复测试同一条旧消息。</p>
<h2 id="总结一下关键步骤">总结一下关键步骤</h2>
<ol>
<li>页面模板加 <code>data-iv-*</code> 语义标记</li>
<li>在 IV 编辑器中编写基于这些标记的规则，发布拿到 <code>rhash</code></li>
<li>Bot 消息用 <code>link_preview_options</code> 挂 IV 链接，同时保留原始链接</li>
<li>部署目录放 <code>.nojekyll</code></li>
<li><strong>部署后轮询确认页面在线，再发通知</strong>——这一条最容易漏，也最关键</li>
</ol>
