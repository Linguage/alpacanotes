13:T147b,<h2 id="问题背景">问题背景</h2>
<p>Telegram 的 Instant View（IV）功能允许用户在客户端内直接阅读网页正文，无需跳转浏览器。对于内容发布者来说，如果链接能附带 IV 按钮，阅读体验会好很多。但在实际适配过程中，同一域名下的链接表现并不一致：有时卡片底部会出现 <code>INSTANT VIEW</code> 按钮，有时只有普通预览；即使首次能正常打开 IV，再次点击同一链接时正文偶尔会变成白屏。</p>
<p>这篇文章记录了一次完整的排查过程，把问题拆分成页面结构、IV 规则、Bot 消息构造、部署链路四个层面逐一检查，最终定位出各层的实际状况。</p>
<h2 id="页面结构从样式类名到语义标记">页面结构：从样式类名到语义标记</h2>
<p>Instant View 模板需要从页面中找到标题、正文、作者等内容。之前的 IV 规则靠 Tailwind 的样式类名（如 <code>text-xl</code>、<code>mt-16</code>）来定位元素。问题在于，前端只要调一下样式，规则就会悄悄失效，而且不会有任何报错提示。</p>
<p>改造方案是给页面关键元素加上专门的 <code>data-iv-*</code> 标记：标题、正文、发布时间各有明确标记，不该被抓取的导航元素也标注了忽略。这样 IV 规则认的是稳定的语义标记而不是随时可能变化的样式类名，页面和规则之间的依赖关系就清晰可控了。</p>
<p>同时修正了 canonical URL 中缺失的部署子路径前缀。这个问题对浏览器访问没有影响，但会导致 Telegram 抓取时拿到一个不存在的“标准地址”，增加了不必要的排查干扰。</p>
<h2 id="iv-规则同域名双模板兼容">IV 规则：同域名双模板兼容</h2>
<p>该域名下同时存在两套页面结构：笔记站使用 <code>data-iv-*</code> 标记，主站文档页用的是完全不同的 HTML 结构。为了用一份 IV 模板覆盖两种页面，规则采用了先后匹配的方式——优先尝试 <code>data-iv-*</code>，匹配不到就回退到主站的页面结构。</p>
<p>这一步的意义不是追求“优雅”的规则，而是承认同域名多模板并存的现实，并在模板层面把这种现实明确表达出来。</p>
<h2 id="bot-消息构造并非照文档填参数就行">Bot 消息构造：并非照文档填参数就行</h2>
<p>页面结构和 IV 规则就绪后，通过裸链接 <code>t.me/iv?url=...&#x26;rhash=...</code> 直接访问，确认 IV 可以正常渲染。这一步排除了“规则未生效”和“<code>rhash</code> 失效”两种可能。</p>
<p>问题出在 Bot 推送消息的环节。Telegram Bot API 提供了指定预览链接的参数，但实测表明，通过它指定 IV 链接并不能稳定重现用户手动粘贴链接时的效果。在某些消息写法下，Telegram 会把 IV 链接当作普通链接处理，甚至解析成别的东西。</p>
<p>经过多轮实验——把 IV 链接嵌在文本里、做成按钮、拆成两条消息、调整预览参数——最终才找到一套可以稳定挂出 IV 卡片的消息写法。这里最重要的结论不是某个参数本身，而是消息的写法会影响 Telegram 生成预览的方式，需要单独测试验证。</p>
<h2 id="部署链路中的两个隐蔽问题">部署链路中的两个隐蔽问题</h2>
<p>排查过程中暴露了两个与 IV 表面无关但实际影响结果的部署问题。</p>
<p>第一个是 <code>.nojekyll</code> 文件缺失。切换到手写 shell 部署后，发布目录中不再自动包含 <code>.nojekyll</code>，导致 GitHub Pages 将 <code>_next</code> 等下划线开头的目录忽略。表现为页面 HTML 可以加载，但 CSS 和 JS 资源全部 404。这个问题的外在表现很容易被误判为前端代码错误。</p>
<p>第二个是发布时序问题。Bot 发送通知时，GitHub Pages 的 CDN 可能尚未完成传播，导致 Telegram 抓取到的是旧版页面或空白响应。解决方式是在部署完成后轮询目标 URL，确认返回 200 且页面包含预期标记后，再等待一段冷却时间才触发通知。</p>
<h2 id="最终结论">最终结论</h2>
<p>经过逐层排查，问题的边界可以明确划分：</p>
<p>站点侧的工作已经基本完成：页面结构有稳定的语义标记，IV 规则不再依赖容易变化的样式类名，部署流程中的 <code>.nojekyll</code> 缺失和发布时序问题已修复，Bot 消息写法也经过验证可以触发 IV 卡片生成。</p>
<p>剩余的不稳定性主要表现为同一条 IV 链接反复打开时偶尔出现白屏。由于首次打开通常正常，失败只出现在重复打开的时候，这更可能是 Telegram 客户端自身的缓存或渲染行为导致的，而不是站点侧的问题。</p>
<p>对于这类不在自身控制范围内的行为，务实的做法是保留原始链接作为阅读兜底，验证时使用新链接而非反复测试同一条旧消息。</p>
